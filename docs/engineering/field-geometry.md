# 球场几何数据字典

唯一输入为 `data/fields.json.geometry`，版本当前 `field-2`，虚拟米，中心原点、x 向右、side 0 视角 y 向下。`FieldDefinitionsSchema` 在 shared/data 导入时验证完整文件；`packages/game-core/src/field.ts` 是唯一墙/网/弹簧边界生成及圆体可容纳性入口，旧 shared/physics 继续重导出。没有皮肤可以携带自己的 geometry、碰撞半径或门宽。

R=原始资料、M=测量、U=用户确认、B=重建。上述标签不提升证据等级，不把代码默认值变成 U。皮肤原图/重建来源仍逐项保留在 fields.json.source；权利见 FND-03。

schema 拒绝非有限数、非正尺寸、横向或超过 3:1 的不支持比例、互相侵占的门/角、越界禁区/中圈/点球点、半关闭小禁区；这个比例范围是工程支持边界，不是原版公式。皮肤拒绝未知字段、重复 ID、非法旋转、反向或超出原图的 crop。渲染与物理共用相同数据，不修改任何现有数值。以后改几何须升级 fieldVersion，同时更新配置哈希、资源清单、校准及物理测试。

`tests/field.test.ts` 断言九套皮肤共用唯一几何、16 段边界两端对称、无退化段和 schema 反例；FLD-03 扩展实际接触与门线行为。`npm run test:physics` 保留完整原校准回归。

## 相机与输入

`packages/game-core/src/camera.ts` 只处理 CSS 像素、内容矩形与世界坐标；worldToView/viewToWorld/clientToWorld 是统一入口。side 1 仅改变相机符号，网络/物理坐标保持原系。fieldViewport 返回 camera、内容矩形、球场矩形和 backing size。DPR 只在画布背板及 cameraMatrix 使用，不在指针输入再次乘除。Renderer 的画面、全窗口瞄准层与 DOM 比分栏都使用此入口；整场背景和顶部比分栏固定朝上，两端球员坐标按相机翻转。

保留现有整场场景的顶部固定布局与底栏预留；程序化场地保留原边距。零尺寸 DOM 暂不更新相机，待可见时重算；无效纯布局输入明确报错。`drag.ts` 提取现有拉距、力量和手势弧线积分，预览与最终出手共用，出手仍按原 3/6 位精度量化。几何与手感常数保持原值。

`npm run test:field` 覆盖 320×568/390×844/768×1024/1440×900，两视角×DPR1/2/3×场景/非场景，共48种布局；每种100个点往返误差小于1e-6，并校验同一世界拖拽的方向/力度/弧线一致。浏览器测试另含鼠标和 CDP touch 原生事件流；这不替代微信和 App 真机验收。

## 碰撞与进球

fieldSegments（16段）生成墙、六段球网和四角弹簧，fieldPosts（四根圆柱）统一生成门柱，fieldOutline 提供八边内轮廓给渲染。球门开口处不存在跨门隐墙；真实 CCD 测试验证球能穿过开口并被网收住，撞柱球不能穿模。

进球使用相邻物理步的足球位置，对“中心超过门线一个球半径”的整体越线阈值求交点，同时验证交点横向容纳整个足球。部分越线、刚好相切、门口外越线和初始已经在界外不触发进球。原实现只有 y 判定，本次补齐既定规则的合法门口与新越线条件；不更改几何、速度或手感数值。ShotRunner 在已有 goal 时不再次判断，同一杆最多一次事件；球网只负责碰撞吸能。

`tests/field-collision.test.ts` 包含上下门的精确门线边界/斜向交点、高速进球/击柱、左右墙/四角和多次接触；逐步检查足球留在容纳边界内。旧物理套件继续覆盖固定步长、随机出手和完整规则比赛。

## 特殊接触与移位

弹簧 begin-contact 仅动态球员且接近速度大于 minSpeed 时登记；按球员ID+角号在同一物理步去重。法线朝内，求解后加力并按既有 maxSpeed 限速；足球只使用普通墙恢复系数，冻结/锚定静态体不受加力。事件保持现有 spring-kick 名称，包含时间、球员、角号、位置和最终速度；contracts 对该事件及唯一ID列表的 relocate 提供严格 schema。

门后球员在本杆未进球结束后一起生成一次 relocate 事件，逐人选择合法空位；冻结/锚定不改变这条规则。freeSpot 保留原近邻环搜索，增加唯一几何内沿检查，以及有界确定网格后备搜索。无合法位置明确失败，不再静默返回重叠点。进球则先计分并复位全部状态，失球方开球，不另外发移位事件。

专项测试覆盖四角法线、超速限幅、低速、足球、静态体、单步去重，以及权威 resolveShot 的多球员移位/防重叠和进球重置组合。全部保留 phys-4 数值。

## 皮肤标定

`fieldArtMapping` 统一处理 source crop → 顺时针0/90/180/270 → 可玩世界矩形及逆变换，并提供 Canvas affine matrix 和场景包围框。裁切生成器仍读取 fields.json；Renderer 整图、已裁切图和HUD使用同一转换。整图纵向改用 length/cropHeight，修正原来沿用 width/cropWidth 导致的下门线约0.00452m偏差；不改物理数据。未来旋转整场时源图也随矩阵旋转，不能只旋转碰撞。

比赛场景使用 field.<id>.scene/art 绑定；大厅 Image_01–05 使用 lobby.stadium.<n> 绑定，仅为等距展示，无碰撞坐标，不将等距图强行套到正交比赛矩形。程序化 orig_2016 的 crop/sceneSize 是虚拟版式；其他三套程序化皮肤直接使用核心几何。

`PLAYWRIGHT_BROWSERS_PATH=<cache> node tools/field-capture.mjs` 自启独立端口Vite并清理，生成 `docs/productization/reports/field-calibration/anchors.json` 和 `skins-both-sides.png`。development独立入口 field-debug.html 不在生产构建入口中。报告区分“变换误差”和“独立原图测量误差”：本次最大2.22e-16m是前者，原图的手绘门框/装饰仍有视觉厚度，不能把数学互逆宣称为重新测得原版常数。18格叠加检查墙内沿、门柱/开口、弹簧、网，以及五张大厅图的用途；FLD-07继续视口与拖拽矩阵。

## 渲染层、画质与释放

Renderer.draw 组合静态场地、阴影、轨迹、棋子、门框前沿、表现特效和瞄准层；HUD仍由GameView单独更新。静态层以皮肤/相机/背板/图片解码状态为key，解码后替换降级图。菜单支持自动/流畅/标准/精细；低端能力/减少动态效果选择较低档。档位只影响DPR背板、阴影/拖尾和特效数量，出手预览与模拟完全不读取该配置。原图网络分辨率变体仍由AST-05承接，当前通过较低背板降低实际绘制纹理大小。

头像LRU最多32张，场地图最多4张，底色最多4项，静态/重绘缓存最多2张。dispose幂等清空图片引用及canvas背板，GameView实际调用它并取消动画、订阅及持有的定时器。特效列表另有128项硬界限，绘制预算按档位降低。

samplePlayback只读服务端毫米帧并转换一次为米，禁止反写frames/MatchState；30/60/120/144Hz终态一致性使用真实物理录制和冻结输入验证。后台恢复丢弃旧回放/移位/拖尾/特效，使用最新权威state并通知host播放结束，不补播旧声音。

浏览器资源工具在DPR3执行15次创建/切换九皮肤/加载40头像/释放循环。390×700画布三档背板分别273000/614250/1706250像素，所有循环释放后缓存计数和背板为0。resources.json记录真实GC前后JS heap观测值；该数值含浏览器与模块缓存噪声，不能推断移动GPU内存或长期运营表现，平台真机仍需对应任务验证。
