# 球场建模、坐标与物理表现

## 1. 建模范围

当前玩法以 2D 物理为权威。这里的“球场建模”包含可玩区域、碰撞体、球门判定、四角弹簧、相机、皮肤映射和渲染层次，不默认引入三维引擎。大厅球场可以是等距插画或轻量动画，比赛仍使用同一套 2D 几何。

以后需要 3D 展示时，只替换表现层；3D 位置投影回物理平面，不能另外维护一套碰撞边界。FLD-07 要交付可视化调试工具与素材坐标对齐证据。

## 2. 唯一几何来源

现有入口：`data/fields.json.geometry`、`shared/physics.ts.fieldSegments()`、`client/src/render.ts`。这些必须经提取后仍使用同一个几何对象；皮肤不允许私自改变门宽或球场比例。

| 参数 | 当前基线 | 说明 |
|---|---:|---|
| width / length | 6.0 / 9.78 m | 虚拟米，不是图片像素 |
| goalWidth / goalDepth | 2.05 / 0.4 m | 上下球门；物理边界包括网深 |
| postRadius | 0.07 m | 门柱为圆形碰撞体 |
| cornerCut | 0.5 m | 四角斜边；弹簧碰撞面沿斜边 |
| boxWidth / boxDepth | 2.65 / 1.32 m | 禁区；不能与装饰图上的误差混用 |
| centerRadius | 1.0 m | 中圈 |
| discRadius / ballRadius | 0.32 / 0.12 m | 来自 physics.json |

来源标记沿用 BASELINE 的 R/M/U/B。修改尺寸必须升级 fieldVersion，重跑物理校准及所有几何场景；禁止为了“看着更像”在渲染里悄悄缩放某个碰撞体。

## 3. 坐标与视角

- 原点是中点；x 向右，y 向下。side 0 守下方，进攻上方；side 1 的视图旋转 180°，比赛坐标不变。
- 所有网络和持久化坐标使用同一世界系。显示上的“我方在下”只由相机变换决定。
- 玩家拖拽先从屏幕点逆变换到世界点，再生成 ShotInput；DPR 只影响画布像素密度，不重复乘到坐标。
- HUD、安全区和画布内容矩形分开；不能把顶部比分条或底部按钮的偏移再次施加到物理坐标。

数学提示（示意，FLD-02 需补布局计算和类型）：

```ts
type Point = { x: number; y: number };
interface Camera { cx: number; cy: number; scale: number; side: 0 | 1 }
function worldToView(p: Point, c: Camera): Point {
  const sign = c.side === 0 ? 1 : -1;
  return { x: c.cx + sign * p.x * c.scale, y: c.cy + sign * p.y * c.scale };
}
function viewToWorld(p: Point, c: Camera): Point {
  const sign = c.side === 0 ? 1 : -1;
  return { x: sign * (p.x - c.cx) / c.scale, y: sign * (p.y - c.cy) / c.scale };
}
```

验收：两种视角、DPR 1/2/3、不同内容矩形，随机点正逆变换误差 <1e-6 世界单位；拖拽相同世界意图产生相同 direction/power/curve。不能以全截图相似代替坐标一致。

## 4. 碰撞体与规则事件

碰撞层至少区分 disc、ball、wall、post、net、spring；调试显示每一类及其法线。边界生成使用 `fieldSegments`，不能在渲染里重写“差不多”的球场轮廓。

- 球员与足球：圆形刚体；技能 fixed/anchor 通过正式规则控制静态/动态状态。
- 边墙：分段线或等效碰撞面，球门开口不能被一条隐藏墙封住。
- 门柱：两端各两个圆形 fixture，检测高速擦柱、近柱进球和不会穿模。
- 球网：门后与两侧约束并吸能，不负责替代进球线。
- 弹簧：只对球员加速；足球按普通墙；法线朝内，限速、最小接近速度与重复接触去重都要验证。

进球是足球**整体**越过门线，且处在合法门口；不得只检查球心进入某张球门图片矩形。上下端方向对称：圆心越过门线超过 ballRadius 才满足整体越线条件，最终以正式物理实现处理运动轨迹与门柱约束。

同一杆只能产生一次有效 goal；goal 后的帧播放、比分更新、重置阵容、失球方开球须有明确状态顺序。球员进入门后而球未进时，按当前规则杆结束后移至门前合法空位，不能每帧瞬移或与其他物体重叠。

## 5. 固定步长与回放

当前数据基线：120 Hz 物理，8/3 迭代，30 Hz 位置记录；渲染按 requestAnimationFrame/平台回调插值。

- 服务端模拟和客户端预测调用同一个物理核心；正式结果只认服务端。
- 回放 frames 是毫米整数坐标；转换为米时只除一次 1000。插值不得反写 MatchState。
- 30/60/120/144 Hz 显示应得到同一权威终态。后台恢复先获取服务端 state/seq，抛弃过期动画。
- 不声明不同 JS 引擎位级确定性；客户端只预测。回放复核保存引擎版本、配置 hash、初态和输入；跨引擎数值容差单独标注。
- 最长模拟时间和最高球速是保险上限；触发时记录指标。不能把每次都强行到时停止当作合格手感。

## 6. 皮肤到物理的映射

现有皮肤使用 artSource、artCrop、artRotate、sceneSize。保留“整张场景”和“裁切可玩区域”两种用途，不能将大厅等距球场图拿来标定比赛碰撞。

资源 manifest 至少记录：id、版本、来源、授权状态、hash、像素尺寸、crop、旋转、锚点、目标几何版本、加载优先级。

对旧全场底图：通过 crop 将内沿映射到世界矩形，scorebar 属于 HUD 标定点。对新原创资源：优先分层制作草坪、墙、门柱、网、弹簧、装饰，避免把可变比分烘焙进背景。

渲染顺序建议：背景/看台 → 草坪/标线 → 后侧球网/墙体 → 阴影 → 棋子/足球 → 门框前沿 → 轨迹/技能 → HUD → 弹窗。物体遮挡应基于明确层或 y 排序；装饰不能挡住出手热区。

## 7. 场景与资源预算

- 比赛主场保留竖向比例；PC 可放大并在两侧容纳阵容/战况，不拉伸球场。
- 原创资源使用逻辑锚点，不用某一台手机的绝对像素布局。
- 高中低画质只影响粒子、阴影、贴图分辨率与回放插值策略，不影响物理、预测长度或技能效果。
- 优先图集/裁切/预载当前场地；不将 raw/cutout 和未引用大图全部打进发布包。
- 目标设备与帧率预算由 WEB/WX/APP 真机测量，FLD-06 提供质量档位切换，不凭猜测统一硬编码 DPR。

## 8. 球场验收矩阵

| 场景 | 必须观察/断言 |
|---|---|
| 正面/斜面撞墙、四角、沿墙起步 | 无穿透、异常反向吸附、持续重叠 |
| 高速擦柱、球部分过线、整体过线 | 判定对称且每杆最多一次进球 |
| 球员与足球撞弹簧 | 只有球员得到额外能量；有上限与冷却/接触去重 |
| 满弧线反墙、碰球/碰人/碰柱 | 撞墙镜面反弯；与球/人/柱/网接触按现行规则消弧 |
| side 1 视角 | 门、准星、拖拽、弧线左右语义一致 |
| 320×568、390×844、768×1024、1440×900 | 物理边界与画面标定一致，HUD 不挡热区 |
| 手机安全区与横竖切换 | 不改变实际 geometry；旋转有明确支持/提示 |
| 低帧率/后台回前台 | 无多发一杆、动画积压或终态回退 |
