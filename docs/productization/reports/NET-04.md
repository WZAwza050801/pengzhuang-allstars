# NET-04 · 可靠结果与事务结算

2026-11-18；Windows / Node 24.22.1 / npm 11.9.0 / 隔离 PostgreSQL 17.12 / Mailpit / Chromium。任务验收完成。全部验证在本机，未使用远端服务器。

账号房开局时将双方参赛关系与结算配置 hash 一次提交；终局先生成冻结意图，再持久保存 outcome/matches/result/outbox。消费者在一个真实数据库事务中更新钱包、不可变账本、资产操作、双方奖励凭证、每日上限/参与卡进度、排名端口及完成标记。终局广播丢失不影响保存和发奖，同局同载荷重试不会新建流水，冲突保留证据并停止自动处理。

实现与接口、故障语义、迁移及后续边界见 [match-settlement.md](../../engineering/match-settlement.md)。只读接口为 `/api/v1/me/matches`、`/api/v1/matches/:id/result`；有会话、必需账号提示、本人权限、分页和 no-store，不暴露对手用户 ID、凭据或 RNG，不提供玩家提交结果/领取奖励的写接口。

真实进程崩溃验收由 `tests/helpers/outcome-worker-child.ts` 与 `tests/outcomes.integration.test.ts` 实施：父进程等待子进程实际到达边界，结束并等待退出，再创建全新服务。三个边界分别为 fsync 日志已发布但连接真实不可达数据库端口、SQL 事务内完成资产/奖励写入但未提交、提交成功但尚未删除日志。恢复后检查两人余额、唯一奖励/账本和 SQL 排名事务标记；每局各一次，文件成功清理。SQL 标记只证明排名端口与资产处于同一事务，没有实现或绑定生产 Elo。

另用真实数据库触发器在钱包、账本、资产操作、奖励记录、outcome 完成时间、outbox processed 位置失败，核对所有资产/奖励/进度/关闭标记随事务回滚，原结果及日志仍在。并发双消费者、同用户八局并发、每日 300 上限、每天一张参与卡及跨日进度沿用 economy-2；当前经济版本变更不会重写历史局的冻结报价。
