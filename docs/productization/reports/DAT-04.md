升级报价来自当前服务器配置：初始 300 金币，升级 1→2 花费 100，2→3 花费 150，余额为 50。首次成功请求在后续升级后重放仍返回原结果，不修改当前资产。八个同 key 并发请求得到同一回执；新服务实例重放同样无新增效果。换目标、载荷或操作类型复用 key 冲突；不同用户的 key 空间独立。不同 key 并发升级同一卡只一项成功；同钱包两个卡升级也不会透支。

配置切换后拒绝旧报价，新报价采用新成本；原成功回执仍可重放。合成校验碎片钱包版本、定义可用性和未持有状态，唯一卡/扣款/回执同事务。外人卡、未知卡、禁用卡、伪造价格/用户/等级、缺失 key、CSRF 拒绝；没有玩家 grant/debit HTTP 入口。封禁后不能通过旧成功回执或内部授予继续操作。

内部授予覆盖大于 2^53 的精确整数、多货币、新卡和重复卡转碎片；同一业务 source 换 key 仍冲突。int64 最大余额可精确增加及扣除，负值、Number 输入、溢出、余额不足均不产生半写。SQL 对账验证初始及后续流水总和等于最终钱包。等待用户锁期间修改原命令/历史 policy 的测试证明服务已复制输入、冻结配置。

通过真实数据库 trigger 分别在钱包、卡、账本、回执、outbox 写入点抛错，均验证整个事务回滚，解除故障后原 key 可成功。另用非事务 sequence 和 trigger 注入 `40P01`/`40001`：前两次失败第三次成功且只有一次效果；持续错误只尝试三次后返回 retryable 503，普通 SQL 故障只一次。这里验证的是 SQLSTATE 重试处理，不冒称构造了真实死锁。真实未提交扣款占用用户锁时，升级请求在 PostgreSQL 等锁（pg_stat_activity 可见），提交后按新余额拒绝透支。

HTTP 响应头成功后主动丢弃响应 body，再以同 key/body 请求得到原回执，资产只变一次。外层业务事务故障回滚内部 grant/debit 和流水。账本在同毫秒、不同微秒记录间分页无重复/漏项，隔离他人流水，非法游标和 year-zero 拒绝，历史 UPDATE/DELETE 被数据库拒绝。最新迁移 down/up 在隔离集群验证。

首次回归发现内部校验同步抛错与默认 outbox 50 条分页的旧测试假设，分别统一内部异步端口错误行为、将该测试自己的 due 事件提前排期；未提高生产分页上限或消费其他测试事件。新增契约文件曾与既有视觉 assets 模块同名，已恢复原模块且无差异，经济契约改用独立名称。最终上述全量验证均通过。
