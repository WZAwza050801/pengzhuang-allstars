## 2. 项目背景

本项目是对已停运游戏《碰撞全明星》的浏览器怀旧复刻：竖屏、5v5 棋子式弹射足球，轮流拖拽出手，支持技能、进球和完整比赛。

当前技术栈：

- 前端：Vite 7 + TypeScript；
- 物理：Planck.js，共享代码位于 `shared/physics.ts`；
- 规则与对局：`shared/match.ts`；
- 数据：`data/*.json`，加载逻辑位于 `shared/data.ts`；
- 本地对局：`client/src/localHost.ts`；
- 渲染与交互：`client/src/game.ts`、`render.ts`、`main.ts`；
- 联机依赖已在 `package.json` 声明：Colyseus 0.16.x、Express、colyseus.js；
- 测试与校准：`tools/`、`npm run test:physics`、`npm run calibrate`。

原始资料与约束位于：

- `materials/pengzhuang_rebuild/README.md`
- `materials/pengzhuang_rebuild/07_ai_handoff/MILESTONES.md`
- `materials/pengzhuang_rebuild/05_online/README.md`
- `materials/pengzhuang_rebuild/05_online/PROTOCOL.md`
- `docs/calibration.md`
- `docs/physics-tests.md`

## 4. 本轮总目标

### V0.2：从“本地可玩”升级为“服务端权威的双人在线可玩”

优先级从高到低：

1. 建立可启动的 Node + Colyseus 服务端；
2. 复用共享物理与规则，由服务端判定出手、技能、比分和结束；

5. 支持重复消息去重、旧回合拒绝、越权拒绝和输入校验；
6. 支持断线保留座位、运动中完成当前杆、停稳后等待和重连恢复；
7. 支持最小持久化与对局检查点；
8. 补齐网络自动化测试、构建和开发文档；
9. 保持本地 hot-seat / bot 模式及全部现有测试不回归。

## 5. 分阶段交付与验收

### 阶段 A：基线与最小联机骨架

任务：

1. 阅读上述资料与现有源码，输出简短架构说明；
2. 复跑 typecheck、physics tests，并记录现有问题；
3. 新建 `server/`，使用现有 Colyseus 0.16.x API，不凭记忆混用旧版本写法；
4. 确保 `npm run dev:server`、`npm run dev:client` 可分别启动；
5. 增加 `/healthz` 健康检查，返回服务状态、协议/数据版本，不返回密钥；
6. 明确开发环境端口与客户端 WebSocket 地址配置，提供 `.env.example`，不得写入真实密钥。

验收：

- 服务端和客户端均能启动；
- typecheck 通过；
- 健康检查可访问；
- 原有 physics tests 全部通过。

### 阶段 B：私人房间与服务端权威一杆球

任务：

1. 实现创建房间、房间码、加入房间、昵称、座位分配、双方 ready；
2. 开局锁定双方 5 人阵容、等级、场地、rules/physics/roster 版本和随机种子；
3. 服务端使用 `createMatch`、`beginTurn`、`validateShot`、`resolveShot` 等现有共享逻辑；
4. 对 `shot` 消息校验：
   - 会话与座位合法；
   - matchId、turnId 为当前值；
   - 当前行动方与棋子归属正确；
   - 所有数字有限，方向有效，power/curve 在范围内；
   - configVersion 一致；
   - `clientShotId` 在该 match 内去重；
5. 服务端产生唯一 `ShotPacket`，两端播放同一组轨迹与事件；
6. 服务端保存停稳后的权威 `MatchState`，客户端不得上传比分或物理结果；
7. 拒绝重复、越权、旧回合和恶意畸形输入，并返回稳定错误码；
8. 保留并完善 `tools/net-tests.ts`，使 `npm run test:net` 真正可执行。

验收：

- 两个独立客户端能进入同一房间并完成多杆交替；
- 两端每个 tick/关键状态、比分、行动方一致；
- 同一 `clientShotId` 重发不施加第二次冲量；
- 非行动方、旧 turnId、他人棋子、NaN/Infinity、越界数值均被拒绝；
- 断线或客户端低帧率不改变服务端结果；
- `npm run test` 通过。

### 阶段 C：OnlineHost 接入现有 UI

任务：

1. 基于 `client/src/host.ts` 的接口实现 `OnlineHost`；
2. 在 `main.ts` 增加明确模式选择：本地双人、人机、私人联机；
3. 处理 `onState`、`onShot`、`onEvents`、座位/连接状态和错误提示；
4. 统一 playbackDone 语义：在线模式下由服务端控制回合推进，不因某一端动画未完成而复制或跳过事件；
5. 重连后用服务端完整快照覆盖本地旧画面；
6. 不在邀请链接、日志或同步状态中暴露会话密钥/重连令牌；
7. 保持桌面和移动端现有操作体验。

验收：

- 玩家无需修改代码即可创建/加入房间；
- 断线重连后比分、棋子位置、技能状态和行动方一致；
- 本地双人、人机模式仍可正常玩；
- 不出现重复进球、重复技能广播、双方同时可操作等问题。

### 阶段 D：时钟、断线与最小持久化

任务：

1. 回合计时与比赛计时以服务端 deadline 为准；
2. 客户端时间只用于显示，不决定超时；
3. 掉线时保留座位 60 秒（使用 `data/rules.json` 中的规则，不硬编码另一套值）；
4. 若掉线时球仍运动，继续完成该杆；停稳后进入等待；
5. 超时按已声明的复刻规则处理，并在 UI 显示原因；
6. 持久化最少包括：访客身份、阵容、对局元数据、回合日志、停稳检查点；
7. 若采用 SQLite，数据库路径通过环境变量配置，提供备份说明；
8. 服务重启默认从最近完整停稳检查点恢复；无法可靠重放时明确标记该杆需重打或该局中止，不伪造结果。

验收：

- 刷新页面可恢复座位；
- 短暂断网可在保留期内回到同一局；
- 运动中掉线不会取消该杆；
- 重启服务后不会凭空改变比分或重复结算；
- 测试覆盖超时、断线、刷新和重复结算。

### 阶段 E：构建、端到端测试与交接

## 7. 强制技术约束

1. **服务端唯一权威**：客户端只提交意图，不提交位置、比分、随机结果或胜负。
2. **共享确定性代码**：在线与本地必须复用 `shared/physics.ts` 和 `shared/match.ts`，不得复制出逐渐分叉的规则实现。
3. **配置版本锁定**：rules/physics/roster 版本开局锁定，不能赛中热更新改变结果。
4. **固定步长**：沿用 120Hz 物理；记录/广播频率按现有设计与实测决定。
5. **幂等**：`clientShotId` 全 match 去重，goal/end/rematch 等事件不可重复生效。
6. **运行时校验**：TypeScript 类型不能替代网络 JSON 校验。
7. **最小依赖**：新增依赖须说明用途；优先使用已声明依赖。
8. **隐私与安全**：密钥只放本地环境变量；文档、日志和提交中不得出现真实 token。
9. **存档边界**：数据库文件不进 Git；提供备份/恢复说明。
10. **兼容本地模式**：不得用联机改造破坏 hot-seat、bot 和现有校准。
