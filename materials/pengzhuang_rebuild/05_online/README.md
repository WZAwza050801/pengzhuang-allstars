# 联机：朋友在另一张网里也能打一局

你拖动鲁尼松手，电脑只发送“鲁尼、方向、0.6力、向左弯0.2”。公网服务器收下这杆球，计算全部碰撞和技能，向你们两人发送同一组位置与比分。朋友关掉Wi-Fi再回来，拿到服务器保存的当前局面，接着玩。

## 首版范围

| 功能 | 复刻要求 |
|---|---|
| 私人房间 | 创建、房号、邀请链接、昵称、双方准备；最多2名正式玩家 |
| 竞技场 | 在线快速匹配入口，把等待玩家配成2人房间；轮流出手 |
| 阵容 | 开局锁定双方5人、卡牌等级、场地与规则版本 |
| 重连 | 建议保留60秒座位；已出手的物理继续，停稳后暂停等人；超时按复刻规则判负 |
| 对局结果 | 服务器结算，按matchId唯一写入，双方收到同一结果 |
| 保存 | 昵称、阵容、结果与已完成回合检查点；不需要支付或复杂账号体系 |

上表的房间与重连时长是本次设计要求，不是已找到的原版参数。竞技场的段位、机器人补位和排名规则没有完整证据，先实现明确可验收的在线配对。

## 谁负责什么

服务器：房间、座位和身份；轮到谁；接受／拒绝出手；固定步进物理；技能随机数与持续状态；进球和比赛结果。

客户端：输入、瞄准、画面、音效；读取服务器状态后插值显示。为了画出瞄准轨迹，可运行共享物理代码的临时世界，但不能上报一个“我算进了”的结果让服务器照收。

Colyseus官方状态同步文档明确由服务器修改同步状态；断线机制可作为座位恢复的基础，仍需自己定义暂停和判负规则。查阅日期2026-11-14：[状态同步](https://docs.colyseus.io/state)、[重连](https://docs.colyseus.io/room/reconnection)。这是框架能力，不是本项目已经完成的实现。

## 一杆球的服务器顺序

1. 收到shot，校验登录会话、matchId、turnId、当前行动方和球员归属。
2. 校验所有数字为有限数，方向可归一化，power在0—1、curve在−1—1，配置版本一致；不信任客户端数值或计时。
3. 用clientShotId去重。同一杆重发返回同一接受结果，不能施加第二次冲量。
4. 锁定出手并在同一个模拟时间点判定技能。服务器写入随机种子／结果、输入、配置版本和出手前完整状态。
5. 共享物理每步推进。建议从120Hz计算、20Hz状态发送起步，按负载实测调整；这些不是原版频率。
6. 完全球过线后只产生一次goal事件；记录goalEventId，开始进球过渡。没有进球则等待所有物体连续停稳，再交换行动方。
7. 每次停稳／进球结束保存检查点。客户端丢包、低帧率或浏览器后台不改变服务器结果。

## 重连与重启分开处理

- 短暂断网：保留座位与房间，客户端用当前SDK支持的重连凭证恢复；凭证不放在邀请链接里。重新连上后以完整服务器快照覆盖旧画面。
- 断线时球还在运动：继续完成这一杆；停稳才进入等待，避免通过断网取消一次坏球。
- 浏览器刷新：按SDK实际生命周期实现保存与恢复凭证，不只验证自动重连这一条路径。
- 服务器进程重启：物理求解器有内部接触状态，单靠x/y/vx/vy不保证能无缝续算运动中一杆。首版恢复上个完整回合检查点，按固定版本重放未完成输入；如重放不能核对则明确宣告该杆重打或对局中止，不伪造比分。

## 少量好友的部署

一个常驻Node实例托管Colyseus房间与API，前端构建文件由同域服务或反向代理提供；外网HTTPS／WSS。SQLite文件放持久化磁盘，定期备份检查点与结果。先单实例，未来真有并发需求再做多实例房间路由与共享状态。

只上传Vite的dist到静态网站不能承载这套房间服务。某些免费实例会休眠或丢失本地SQLite，例如Render官方免费方案文档列出15分钟无入站流量休眠及本地文件易失限制（2026-11-14查阅）；因此不能把这类磁盘当永久存档。具体套餐和价格在实际部署时再核对：[Render免费实例文档](https://render.com/docs/free)。

部署交付须包含：实际环境变量示例（无密钥）、持久化挂载路径、反向代理WebSocket设置、健康检查、启动与重启命令、备份恢复说明，以及一台电脑加另一网络手机完整打完一局的记录。不能仅用两个localhost标签页证明公网联机完成。
