## 4. 工期估算方法（必须遵守）

**唯一可信的历史耗时在 `runs/WATCHER_V2.log` 和 `runs/WATCHER_V4.log`**，格式：
```
#N ended rc=0 dur=4903s bytes=1471 progress 6581->9087B
```
`dur` = 该 Claude 会话真实墙钟秒数；`progress` 增量 = 实际推进的阶段。

1. 解析这两份日志，列出**每次会话**的 dur / 起止 / rc / 产出字节 / 推进阶段。
2. **剔除失败会话**（rc≠0 且 bytes 极小 = 崩溃/卡死），只用成功会话建立「阶段 → 实际耗时」样本。
3. 明确指出历史样本里**多少是崩溃重跑**（这决定真实时间损耗）。
4. 用 `runs/PROGRESS_ALL.md` 时间戳交叉验证每阶段从开工到 PASS 的墙钟跨度。

**类比基线**：把每个已完成阶段（A/B/C/T1/T2-a/美术 v2）换算成「产出物规模 → 耗时」，用这个关系外推剩余任务。

**绝不能**：把「一个会话跑多久」当「一个任务要多久」。任务耗时 = 净工作 + 回归验证 + **返工**（历史返工率算进去）+ 卡死重启损耗。

## 5. 输出格式（`runs/V04_TIME_ESTIMATE.md`）

### 一、总览
- 结论段：V0.4 全部完成的**总预估工期**（乐观/中性/悲观，机时），以及**多少可由 watcher 无人值守完成、多少必须人工介入**。
- 明确「机时」定义（1 机时 = 1 个 Claude 会话满负荷工作 1 小时）。
- 一句话说最大不确定性在哪。

### 二、逐任务估算表（核心）
每个 T 项一行，字段齐全：

| 任务 | 交付物（具体到文件/功能点） | 前置依赖 | 估算规模 | 净工作机时 | 回归验证机时 | 返工风险 | 乐观/中性/悲观合计 | 阻塞点 |

每项**必须给依据**（例：「T4-a 净工作 ≈1.5 机时 —— 依据 T2-a 同类导入实际 X 机时 + 2250 条是 players 的 21 倍但结构更规整；回归 6 条命令 ≈ Y 机时」）。

### 三、关键路径
依赖关系（文字版），标出可并行与必须串行的任务，指出**关键路径是哪条链、多长**。

### 四、回归与验证成本
- 单次全量回归（6 条命令）耗时区间
- 每类改动需重跑几次回归（改物理数据 vs 只改数据文件 vs 只改 UI）
- **哪些改动连锁影响 `configVersion` / 校准基线 / 176 条 net 用例**（最大的工期风险源，单独点出）

### 五、风险登记
至少 5 条：风险 / 触发条件 / 影响（多少机时）/ 缓解措施。**必须包含**：
- 会话崩溃（3 次实证：Autocompact thrashing ×2 + "Prompt is too long" ×1）
- 端口/文件冲突（并发会话）
- 材料包语义歧义（`probabilities` 是列表不是概率、`duration` 是计数不是秒、`radian` 不是弧度、`weight` 不是 kg）
- 20 条 card vs card_attr 冲突、8 条 issues、待确认人物（小罗 40109 / 卡队 / 齐祖 90001 / 耳帝原名冲突）
- 物理连锁改动导致回归失败
- 公网部署不可执行（只能出文档）

### 六、需要安安确认的决策点
必须由人拍板、否则 agent 无法继续的点（球门宽度最终取值、原版头像 vs 重绘头像默认哪个、公网部署选型等）。每条给「推荐默认选项 + 影响」。

### 七、加速选项
不改产品范围前提下怎么更快（回归频率、先做哪几项收益最大、哪些任务可合并到同一会话省冷启动开销）。**具体到可执行建议**。

### 八、估算自评
诚实标注可信度：哪些数字实测、哪些外推、哪些不确定性最大。
